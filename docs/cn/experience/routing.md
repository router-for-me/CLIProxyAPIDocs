# 路由与请求

## 适用版本与边界

本页收录的做法只对照钉住提交 `911f49cbd49f4fe2516979754a7488a3fd14fe64` 里仍然存在的配置、路由或命令。本页不是官方行为承诺。密钥、Cookie、邮箱、授权文件和用户请求正文都没有抄入。

## 短做法

- <a id="exp-routing-same-model-name"></a>**同名模型共用路由策略**（`exp.routing.same-model-name`）。现象：多个提供商、OAuth 凭证或 API key 发布了同一个模型名。做法：这些凭证都进入 routing.strategy，没有单独的按提供商挑选器。Antigravity 名字不稳定时不会并进同一组。要把客户端看到的名字分开，用模型别名，而不是再加一种网关模式。来源 issue：[#48](https://github.com/router-for-me/CLIProxyAPI/issues/48)、[#178](https://github.com/router-for-me/CLIProxyAPI/issues/178)、[#197](https://github.com/router-for-me/CLIProxyAPI/issues/197)、[#737](https://github.com/router-for-me/CLIProxyAPI/issues/737)、[#893](https://github.com/router-for-me/CLIProxyAPI/issues/893)、[#2369](https://github.com/router-for-me/CLIProxyAPI/issues/2369)、[#2425](https://github.com/router-for-me/CLIProxyAPI/issues/2425)、[#5983](https://github.com/router-for-me/CLIProxyAPI/issues/5983)。对应官方页：[上游模型别名](/cn/accounts/api-keys-models)、[上游 API 密钥](/cn/accounts/api-keys-api)、[Codex 登录](/cn/accounts/codex)、[OAuth 目录、别名与排除](/cn/accounts/oauth)、[路由策略](/cn/routing/strategy)。
- <a id="exp-routing-fill-first"></a>**用 fill-first 用满一个凭证**（`exp.routing.fill-first`）。现象：希望同一个模型先用完一个账号，而不是每个请求都轮询。做法：把 routing.strategy 设为 fill-first。匹配凭证按固定顺序取第一个仍可用的，直到它不能再服务，而不是每请求轮询。来源 issue：[#768](https://github.com/router-for-me/CLIProxyAPI/issues/768)、[#784](https://github.com/router-for-me/CLIProxyAPI/issues/784)、[#845](https://github.com/router-for-me/CLIProxyAPI/issues/845)、[#937](https://github.com/router-for-me/CLIProxyAPI/issues/937)、[#1304](https://github.com/router-for-me/CLIProxyAPI/issues/1304)。对应官方页：[路由策略](/cn/routing/strategy)。
- <a id="exp-routing-round-robin-skip"></a>**轮询会跳过不能服务的凭证**（`exp.routing.round-robin-skip`）。现象：开了 round-robin 仍觉得流量集中在少数账号。做法：默认策略会按模型记住游标，并跳过当前不能服务的凭证，所以看起来像先打满一个账号。刷新凭证后游标仍按模型保留。这不是随机策略。来源 issue：[#1021](https://github.com/router-for-me/CLIProxyAPI/issues/1021)、[#2470](https://github.com/router-for-me/CLIProxyAPI/issues/2470)、[#2611](https://github.com/router-for-me/CLIProxyAPI/issues/2611)。对应官方页：[路由策略](/cn/routing/strategy)。
- <a id="exp-routing-disable-cooling"></a>**关闭冷却以保持凭证可选**（`exp.routing.disable-cooling`）。现象：上游连续出错后出现 auth_unavailable，或模型从列表里消失。做法：把 routing.cooldown.disable-cooling 设为 true。凭证或提供商上的显式值优先。这样失败不会再把凭证冷却出选择。没有另一个 cooldown-duration 键。来源 issue：[#976](https://github.com/router-for-me/CLIProxyAPI/issues/976)、[#1072](https://github.com/router-for-me/CLIProxyAPI/issues/1072)、[#1712](https://github.com/router-for-me/CLIProxyAPI/issues/1712)、[#2107](https://github.com/router-for-me/CLIProxyAPI/issues/2107)、[#2261](https://github.com/router-for-me/CLIProxyAPI/issues/2261)、[#2687](https://github.com/router-for-me/CLIProxyAPI/issues/2687)、[#2855](https://github.com/router-for-me/CLIProxyAPI/issues/2855)、[#3707](https://github.com/router-for-me/CLIProxyAPI/issues/3707)、[#4706](https://github.com/router-for-me/CLIProxyAPI/issues/4706)。对应官方页：[Codex 登录](/cn/accounts/codex)、[OAuth 目录、别名与排除](/cn/accounts/oauth)、[OpenAI Chat](/cn/api/openai-chat)、[冷却](/cn/routing/cooldown)。
- <a id="exp-routing-cooldown-until-reset"></a>**429 后按恢复时间跳过该模型**（`exp.routing.cooldown-until-reset`）。现象：某个账号报 429 或额度用尽后，后续请求不再选它。做法：代理按错误给出的恢复时间冷却该模型，选择时跳过，直到时间到。冷却按模型记录。令牌刷新不要求先关闭凭证文件。其他同模型凭证只在这份冷却仍然生效时被跳过。来源 issue：[#1456](https://github.com/router-for-me/CLIProxyAPI/issues/1456)、[#2593](https://github.com/router-for-me/CLIProxyAPI/issues/2593)、[#2632](https://github.com/router-for-me/CLIProxyAPI/issues/2632)、[#3655](https://github.com/router-for-me/CLIProxyAPI/issues/3655)、[#4508](https://github.com/router-for-me/CLIProxyAPI/issues/4508)、[#5286](https://github.com/router-for-me/CLIProxyAPI/issues/5286)。对应官方页：[反重力登录](/cn/accounts/antigravity)、[Codex 登录](/cn/accounts/codex)、[模型目录](/cn/introduction/models)、[OAuth 目录、别名与排除](/cn/accounts/oauth)、[冷却](/cn/routing/cooldown)、[路由策略](/cn/routing/strategy)。
- <a id="exp-routing-session-affinity"></a>**打开会话粘性保住加密推理**（`exp.routing.session-affinity`）。现象：Responses 对话在凭证之间切换后，加密推理内容对不上。做法：把 routing.session-affinity 设为 true，让同一会话留在同一凭证。默认是 false。粘性不能代替上游已经作废的加密内容。来源 issue：[#1793](https://github.com/router-for-me/CLIProxyAPI/issues/1793)、[#3189](https://github.com/router-for-me/CLIProxyAPI/issues/3189)、[#3884](https://github.com/router-for-me/CLIProxyAPI/issues/3884)。对应官方页：[Responses](/cn/api/responses)、[路由策略](/cn/routing/strategy)。
- <a id="exp-routing-priority-before-strategy"></a>**优先级耗尽后才轮询**（`exp.routing.priority-before-strategy`）。现象：调高 priority 后仍期望它按权重和其他凭证分摊流量。做法：更高的 priority 会先被用到耗尽，之后才应用 routing.strategy。priority 不是 weight。来源 issue：[#3288](https://github.com/router-for-me/CLIProxyAPI/issues/3288)、[#4502](https://github.com/router-for-me/CLIProxyAPI/issues/4502)。对应官方页：[凭证优先级](/cn/accounts/api-keys-priority)、[路由策略](/cn/routing/strategy)。
- <a id="exp-routing-per-credential-proxy"></a>**为单个凭证指定代理**（`exp.routing.per-credential-proxy`）。现象：只想让某一个账号走代理，其他上游仍用全局设置。做法：全局默认仍是 requests.proxy-url。OAuth 凭证 JSON 写入 proxy_url 只覆盖该账号。Claude、Gemini、Codex 的 API key 条目使用各自的 proxy-url。来源 issue：[#304](https://github.com/router-for-me/CLIProxyAPI/issues/304)、[#690](https://github.com/router-for-me/CLIProxyAPI/issues/690)、[#847](https://github.com/router-for-me/CLIProxyAPI/issues/847)、[#1160](https://github.com/router-for-me/CLIProxyAPI/issues/1160)、[#1236](https://github.com/router-for-me/CLIProxyAPI/issues/1236)、[#1290](https://github.com/router-for-me/CLIProxyAPI/issues/1290)。对应官方页：[按密钥代理](/cn/accounts/api-keys-proxy)、[出站请求](/cn/routing/requests-value)。
- <a id="exp-routing-proxy-for-token-exchange"></a>**让服务器自己经代理完成登录**（`exp.routing.proxy-for-token-exchange`）。现象：登录或配额查询失败，但本机浏览器或系统代理是通的。做法：令牌交换使用服务器自己的出网。设置 requests.proxy-url，容器里不要填宿主机的 localhost。Claude 登录走 uTLS 时用 socks5，不要用 HTTP 代理。Codex 刷新令牌不读取凭证文件里的代理，这时用全局 proxy-url。来源 issue：[#480](https://github.com/router-for-me/CLIProxyAPI/issues/480)、[#1186](https://github.com/router-for-me/CLIProxyAPI/issues/1186)、[#1213](https://github.com/router-for-me/CLIProxyAPI/issues/1213)、[#1217](https://github.com/router-for-me/CLIProxyAPI/issues/1217)、[#1256](https://github.com/router-for-me/CLIProxyAPI/issues/1256)、[#1376](https://github.com/router-for-me/CLIProxyAPI/issues/1376)、[#1749](https://github.com/router-for-me/CLIProxyAPI/issues/1749)、[#2050](https://github.com/router-for-me/CLIProxyAPI/issues/2050)、[#2180](https://github.com/router-for-me/CLIProxyAPI/issues/2180)、[#2934](https://github.com/router-for-me/CLIProxyAPI/issues/2934)、[#2943](https://github.com/router-for-me/CLIProxyAPI/issues/2943)。对应官方页：[反重力登录](/cn/accounts/antigravity)、[Claude 登录](/cn/accounts/claude)、[Codex 登录](/cn/accounts/codex)、[使用 Docker Compose](/cn/docker/docker)、[出站请求](/cn/routing/requests-value)。
- <a id="exp-routing-management-page-download"></a>**让管理页文件能够下载**（`exp.routing.management-page-download`）。现象：管理页 404，或容器里缺少 management.html。做法：management.html 在运行时下载，不打进镜像。确认 requests.proxy-url 可达且未过期，并避开 GitHub 限流。disable-control-panel 为 true 时不会提供面板。Docker 里改完 management secret-key 后重建容器。来源 issue：[#557](https://github.com/router-for-me/CLIProxyAPI/issues/557)、[#711](https://github.com/router-for-me/CLIProxyAPI/issues/711)、[#966](https://github.com/router-for-me/CLIProxyAPI/issues/966)、[#2378](https://github.com/router-for-me/CLIProxyAPI/issues/2378)、[#2913](https://github.com/router-for-me/CLIProxyAPI/issues/2913)、[#6178](https://github.com/router-for-me/CLIProxyAPI/issues/6178)。对应官方页：[管理端设置](/cn/operations/management-settings)、[使用 Docker Compose](/cn/docker/docker)、[出站请求](/cn/routing/requests-value)、[其他入口](/cn/api/openai-other)。
- <a id="exp-routing-filter-rejected-fields"></a>**用载荷过滤去掉上游拒绝的字段**（`exp.routing.filter-rejected-fields`）。现象：Codex、DeepSeek、GLM、NVIDIA 或 Grok 拒绝 response_format、metadata、extra_body 或其他字段。做法：在 requests.payload.filter 的 params 中列出要删除的 JSON 路径。过滤在默认规则和覆盖规则之后执行。来源 issue：[#1647](https://github.com/router-for-me/CLIProxyAPI/issues/1647)、[#2352](https://github.com/router-for-me/CLIProxyAPI/issues/2352)、[#3301](https://github.com/router-for-me/CLIProxyAPI/issues/3301)、[#3577](https://github.com/router-for-me/CLIProxyAPI/issues/3577)、[#4105](https://github.com/router-for-me/CLIProxyAPI/issues/4105)、[#4149](https://github.com/router-for-me/CLIProxyAPI/issues/4149)、[#5112](https://github.com/router-for-me/CLIProxyAPI/issues/5112)、[#5648](https://github.com/router-for-me/CLIProxyAPI/issues/5648)。对应官方页：[上游基础地址](/cn/accounts/api-keys-base)、[xAI 登录](/cn/accounts/xai)、[过滤载荷规则](/cn/routing/requests-filter)、[Responses](/cn/api/responses)。
- <a id="exp-routing-keepalive-is-not-json"></a>**保活标记不是 JSON 响应**（`exp.routing.keepalive-is-not-json`）。现象：OpenRouter 流里出现保活标记，被客户端当成坏 JSON。做法：这些标记会随 OpenAI 兼容流转发。它们不是一份 JSON 响应。保活间隔用 requests.streaming.keepalive-seconds。来源 issue：[#417](https://github.com/router-for-me/CLIProxyAPI/issues/417)。对应官方页：[上游基础地址](/cn/accounts/api-keys-base)、[流式保活](/cn/routing/requests-keepalive)。
- <a id="exp-routing-fork-alias-for-image-size"></a>**用 fork 别名区分图像尺寸**（`exp.routing.fork-alias-for-image-size`）。现象：想用不同的图像尺寸，但没有对应的内置模型 id。做法：把 oauth-model-alias 的 fork 设为 true 得到单独 id，再为该别名设置 payload 默认参数。fork 不是 true 时，重复别名只会改名。来源 issue：[#1044](https://github.com/router-for-me/CLIProxyAPI/issues/1044)、[#2546](https://github.com/router-for-me/CLIProxyAPI/issues/2546)。对应官方页：[上游模型别名](/cn/accounts/api-keys-models)、[OAuth 目录、别名与排除](/cn/accounts/oauth)、[默认载荷规则](/cn/routing/requests-default)。
- <a id="exp-routing-gemini-image-config-path"></a>**图像尺寸写在 imageConfig**（`exp.routing.gemini-image-config-path`）。现象：Gemini 图像尺寸和比例没有生效。做法：用 payload 默认参数写到 generationConfig.imageConfig，不要写在 generationConfig 顶层。来源 issue：[#1089](https://github.com/router-for-me/CLIProxyAPI/issues/1089)。对应官方页：[OAuth 目录、别名与排除](/cn/accounts/oauth)、[默认载荷规则](/cn/routing/requests-default)。
- <a id="exp-routing-responses-cache-key"></a>**responses 靠共享缓存键轮换**（`exp.routing.responses-cache-key`）。现象：Codex responses 在账号之间切换。做法：轮换使用共享的 prompt_cache_key。钉住路由不支持 previous_response_id。长对话的提示缓存不依赖 session-affinity。来源 issue：[#1382](https://github.com/router-for-me/CLIProxyAPI/issues/1382)、[#2811](https://github.com/router-for-me/CLIProxyAPI/issues/2811)。对应官方页：[Codex 登录](/cn/accounts/codex)、[Responses](/cn/api/responses)、[路由策略](/cn/routing/strategy)。
- <a id="exp-routing-filter-effort-without-budget"></a>**过滤 reasoning_effort 时不要同时给预算**（`exp.routing.filter-effort-without-budget`）。现象：payload.filter 没有去掉 reasoning_effort。做法：只有请求没有同时设置思考预算时，过滤才会去掉 reasoning_effort。来源 issue：[#1740](https://github.com/router-for-me/CLIProxyAPI/issues/1740)。对应官方页：[过滤载荷规则](/cn/routing/requests-filter)。
- <a id="exp-routing-override-is-final"></a>**载荷覆盖在思考后缀之后仍生效**（`exp.routing.override-is-final`）。现象：模型名上的思考后缀把覆盖规则改回去了。做法：payload.override 在思考后缀之后执行，并且是最后一次业务改写。过大的 max_tokens 也可以在到达 DeepSeek 之前用它改写。来源 issue：[#2404](https://github.com/router-for-me/CLIProxyAPI/issues/2404)、[#2758](https://github.com/router-for-me/CLIProxyAPI/issues/2758)。对应官方页：[上游基础地址](/cn/accounts/api-keys-base)、[覆盖载荷规则](/cn/routing/requests-override)。
- <a id="exp-routing-retry-503"></a>**503 按重试轮次处理**（`exp.routing.retry-503`）。现象：503 被当成需要长时间等待的限流。做法：503 按暂时不可用处理，是否再试由 routing.retry.request-retry 决定，不是一段限流延迟。来源 issue：[#2877](https://github.com/router-for-me/CLIProxyAPI/issues/2877)。对应官方页：[路由策略](/cn/routing/strategy)。
- <a id="exp-routing-gpt-image-override"></a>**gpt-image-2 通过覆盖后的聊天补全调用**（`exp.routing.gpt-image-override`）。现象：把 gpt-image-2 当成普通聊天模型 id。做法：需要载荷覆盖时，经聊天补全调用，并设置图像的基础聊天模型。它不是一条独立的旧图像编辑命令。来源 issue：[#2961](https://github.com/router-for-me/CLIProxyAPI/issues/2961)。对应官方页：[图像、语音与视频](/cn/api/media)、[覆盖载荷规则](/cn/routing/requests-override)、[OpenAI Chat](/cn/api/openai-chat)。
- <a id="exp-routing-force-prefix-off"></a>**无前缀请求失败时检查强制前缀**（`exp.routing.force-prefix-off`）。现象：gpt-image-2 或无前缀请求选不到凭证。做法：routing.force-model-prefix 为 true 时，无前缀请求只使用无前缀凭证。不需要这个限制时设为 false。claude 的 prefix 是凭证自己的前缀。来源 issue：[#2965](https://github.com/router-for-me/CLIProxyAPI/issues/2965)、[#4474](https://github.com/router-for-me/CLIProxyAPI/issues/4474)。对应官方页：[模型名前缀](/cn/accounts/api-keys-prefix)、[路由策略](/cn/routing/strategy)。
- <a id="exp-routing-alias-and-override-effort"></a>**别名加覆盖表达 Opus 努力值**（`exp.routing.alias-and-override-effort`）。现象：想为不同 Opus 努力值准备不同入口。做法：用 oauth-model-alias 配合 payload.override，并沿用括号后缀的写法。来源 issue：[#3126](https://github.com/router-for-me/CLIProxyAPI/issues/3126)。对应官方页：[OAuth 目录、别名与排除](/cn/accounts/oauth)、[覆盖载荷规则](/cn/routing/requests-override)、[Claude Messages](/cn/api/claude-messages)。
- <a id="exp-routing-fill-first-recovers"></a>**fill-first 会在额度恢复后回到先前账号**（`exp.routing.fill-first-recovers`）。现象：不希望额度恢复后自动回到之前的账号。做法：fill-first 会在凭证恢复后重新使用它。若要按天轮换，用管理凭证接口自己切换，而不是新增路由策略。来源 issue：[#3429](https://github.com/router-for-me/CLIProxyAPI/issues/3429)、[#3711](https://github.com/router-for-me/CLIProxyAPI/issues/3711)。对应官方页：[管理凭证](/cn/management/v8-credentials)、[路由策略](/cn/routing/strategy)。
- <a id="exp-routing-override-extra-body"></a>**用覆盖规则增加 extra_body**（`exp.routing.override-extra-body`）。现象：客户端需要一个非标准的 extra_body。做法：把它写进 payload.override 的参数。覆盖作用在上游正文上，不会打印到控制台。来源 issue：[#4203](https://github.com/router-for-me/CLIProxyAPI/issues/4203)、[#4453](https://github.com/router-for-me/CLIProxyAPI/issues/4453)。对应官方页：[上游基础地址](/cn/accounts/api-keys-base)、[模型思考能力](/cn/configuration/thinking-models)、[覆盖载荷规则](/cn/routing/requests-override)。
- <a id="exp-routing-separate-payload-by-model"></a>**不同模型使用不同的覆盖规则**（`exp.routing.separate-payload-by-model`）。现象：同一条 xhigh 覆盖让 gpt-5.5 失败，gpt-5.6 却正常。做法：为 gpt-5.5 和 gpt-5.6 分开写 payload 规则。适合 5.6 的 xhigh 不要套到 5.5。来源 issue：[#4263](https://github.com/router-for-me/CLIProxyAPI/issues/4263)。对应官方页：[模型思考能力](/cn/configuration/thinking-models)、[覆盖载荷规则](/cn/routing/requests-override)。
- <a id="exp-routing-tune-retry-and-cooling"></a>**429 重试用现有重试和冷却**（`exp.routing.tune-retry-and-cooling`）。现象：反复出现 429 的重试上限。做法：调整 routing.retry.request-retry 和冷却开关。不要新增选择器。账号级 HTTP 400 不会换凭证，它按错误请求处理。来源 issue：[#4327](https://github.com/router-for-me/CLIProxyAPI/issues/4327)、[#4846](https://github.com/router-for-me/CLIProxyAPI/issues/4846)。对应官方页：[冷却](/cn/routing/cooldown)、[路由策略](/cn/routing/strategy)。
- <a id="exp-routing-override-grok-subagent"></a>**用载荷覆盖修补 Grok 子代理**（`exp.routing.override-grok-subagent`）。现象：Grok 子代理调用失败。做法：对 grok-4.5 写一条 payload.override。这只改上游正文，不保证所有子代理错误都能消除。来源 issue：[#4439](https://github.com/router-for-me/CLIProxyAPI/issues/4439)。对应官方页：[xAI 登录](/cn/accounts/xai)、[覆盖载荷规则](/cn/routing/requests-override)。
- <a id="exp-routing-compat-shares-strategy"></a>**兼容提供商共用同一路由策略**（`exp.routing.compat-shares-strategy`）。现象：以为 OpenAI 兼容提供商有独立的路由策略。做法：它们已经和别的凭证共用 routing.strategy 与 priority。提供商 name 不是另一套策略开关。来源 issue：[#6284](https://github.com/router-for-me/CLIProxyAPI/issues/6284)。对应官方页：[OpenAI 兼容提供商名称](/cn/accounts/api-keys-name)、[路由策略](/cn/routing/strategy)。
